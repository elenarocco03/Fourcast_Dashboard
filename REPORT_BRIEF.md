# Report brief

Instructions for the agent (Claude, Codex) that helps write the project report.
Read together with `AGENT.md`. Deadline: **20 January 2027**.

## What the report is

A written account of what we did in the Fourcast project: the yield curve models listed
in `TEACHER_INSTRUCTIONS` and the dashboard that shows them. For **each model and each
variant** it says **what we did, how, and which decisions we took and why**.

- **Reader:** someone who knows fixed income and the course material but has never seen
  our project or our conversations. Every section must make sense on its own. Use
  technical terms without explaining the basics.
- **Length:** at most ~10 pages including figures and tables (about 4,000 words).
- **Style:** comprehensive but essential. Say each thing once; give each equation once
  and refer back to it. Leave out marginal details (GUI styling, API keys, caching,
  debugging history, things we tried and dropped unless the reason matters).
- **Close to final:** write deliverable prose, not notes. English.

## Sources of truth (read before writing)

1. `TEACHER_INSTRUCTIONS`: the required models and variants; the report follows this list.
2. The code and what it outputs: **this is what we did**. Every number in the report
   must come from running our scripts. Never invent or round off results by hand; if a
   number is not available yet, write `[TODO: ...]`.
3. `MODELS_PLAN.md` and the git log (commit messages): the decisions and their reasons.
4. `theory/md/models_reference.md` (formulas with page references) and `theory/md/`:
   notation and theory. Use the notation of the course (Mele notes, Tutorials 1-4).

If the code and the plan disagree, the report describes the code, and you tell the user
about the mismatch. If a decision has no recorded reason, **ask the user**; do not make
one up.

## Structure (page budget in brackets)

1. **Introduction** (0.5): goal, the three models, what the dashboard does.
2. **Data** (0.5-1): FRED constant-maturity Treasury yields; sample and frequency;
   maturities used; units; par yields treated as zero yields (state it as a simplification).
3. **Model 1: PCA** (2)
4. **Model 2: Vasicek** (3), with its variants in the teacher's order:
   1. replication with the inputs of the slides (validation against Mele p. 122);
   2. estimation: AR(1) of the short rate on itself for kappa, rbar, sigma; lambda by least
      squares between model and market;
   3. the discrete-time model.
5. **Model 3: Vasicek plus one PCA factor** (2)
6. **Dashboard** (1): how the models are wired in and what the user can do with them.
7. **Limitations and conclusions** (0.5)

References at the end: course material with page numbers, plus literature only if the
user has checked it.

## Template for each model section

- **Objective:** one or two sentences.
- **Model:** the key equations only, with references to the course material.
- **Implementation:** data used, estimation steps in order, the inputs and outputs of each
  step. Mention a file name only where it helps the reader find the code.
- **Decisions:** a short table, *Decision | Alternative | Reason*. Include only choices
  that affect the results (e.g. levels vs changes in PCA, sample start, frequency,
  short-rate proxy, how lambda is obtained).
- **Results:** at most one or two figures and one table, each referenced in the text, then
  2-4 sentences of interpretation (what the numbers mean, not what the figure shows).
- **Limitations:** only those that matter for reading the results (e.g. persistence close
  to 1 makes rbar unstable; one factor cannot fit every curve shape).

## Figures and tables

- Generated by our MATLAB scripts, saved in `report/figures/`, same style throughout;
  never redrawn by hand.
- About 6-8 figures in total. Every figure has a caption that can be read on its own
  (sample, frequency, units).

## Workflow

- Draft in `report/report.md` (Markdown with LaTeX math); the final format is the user's
  choice.
- Write or update a section as soon as its model is finished; do not wait for the end.
- At every update, list for the user: open points, `[TODO]`s, and any mismatch between
  the code, `MODELS_PLAN.md` and `TEACHER_INSTRUCTIONS`.
